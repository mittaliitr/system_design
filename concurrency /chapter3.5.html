The Problem with Regular Locks

ReentrantLock and synchronized are exclusive.
Even readers block each other → unnecessary contention.

Use Case: Cache, configuration, analytics dashboard — thousands of reads, rare writes

ReadWriteLock rw = new ReentrantReadWriteLock();
Lock readLock = rw.readLock();
Lock writeLock = rw.writeLock();

public String get() {
    readLock.lock();
    try {
        return cache.get(key);
    } finally {
        readLock.unlock();
    }
}

public void put(String value) {
    writeLock.lock();
    try {
        cache.put(key, value);
    } finally {
        writeLock.unlock();
    }
}

StampedLock: Lock-Free Reads (Java 8+)

StampedLock sl = new StampedLock();

public Point getPosition() {
    long stamp = sl.tryOptimisticRead();
    int x = this.x, y = this.y;

    if (!sl.validate(stamp)) {
        stamp = sl.readLock();   // Fallback to pessimistic
        try {
            x = this.x; y = this.y;
        } finally {
            sl.unlockRead(stamp);
        }
    }
    return new Point(x, y);
}
Optimistic read: No lock → zero contention
Validate: Check if write occurred
Fallback: Upgrade to real read lock if needed
Use StampedLock when:
to Reads are 99.9%+ of operations
to You can tolerate occasional retry
to Maximum performance is critical

Key Takeaways

1. Regular locks = exclusive → readers block readers

2. ReentrantReadWriteLock = many readers OR one writer

3. StampedLock = lock-free optimistic reads + validate

4. Use ReadWriteLock for caches, configs, dashboards

5. Use StampedLock only when you measure contention

6. ConcurrentHashMap uses StampedLock internally!
