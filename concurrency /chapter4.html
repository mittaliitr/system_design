0.4 Memory Model & Cache Coherence

Ensuring Consistent Views in a Multi-Core World

Chapter 0 – Computer Architecture & Concurrency Foundations

Picture This: A Shared Kitchen

Multiple chefs (CPU cores) share one fridge (memory). Chef A updates the inventory (writes data), but Chef B sees the old list (stale cache). Chaos ensues!

Analogy: The memory model is the "house rule" ensuring everyone sees the latest fridge contents. Cache coherence is the magic that syncs copies automatically.

What is a Memory Model?

The memory model defines how and when changes to memory are visible to different parts of the system (cores, threads).

Core Idea: In single-core, it's simple. Multi-core? Changes must propagate — or bugs happen!

Cache Coherence: The Sync Magic

Each core has its own cache. Coherence ensures all caches reflect the same value for shared data.

1
Core 1 writes to X → Updates its cache & invalidates others
2
Core 2 reads X → Cache miss! Fetches latest from memory
3
Protocol (e.g., MESI) handles states: Modified, Exclusive, Shared, Invalid
4
Snooping or Directory-based to monitor changes
// Java: Without coherence, this could fail!
volatile int x = 0;  // Forces visibility

Thread1: x = 42;     // Write to memory

Thread2: System.out.println(x);  // Sees 42, thanks to model!

Common Memory Models

Different systems guarantee different levels of consistency:

Sequential Consistency
All operations appear atomic & in program order
Relaxed (Weak)
Allows reordering for speed (e.g., ARM)
Release-Acquire
Writes before release visible after acquire
Java Memory Model (JMM)
Happens-before guarantees via sync/volatile
Trade-off: Stronger models = safer but slower. Weaker = faster but need barriers.

Memory Model in Java Concurrency

Java's JMM ensures:

  • synchronized: Full barrier, flushes caches
  • volatile: Read/write visibility across threads
  • Final fields: Immutable after construction
  • Happens-before: Defines ordering (e.g., thread start before join)
// Bug without volatile: Thread2 may see stale value
volatile boolean ready = false;

Thread1: ready = true;

Thread2: if (ready) { ... }  // Guaranteed to see true!
Pro Tip: JMM abstracts hardware — but understanding coherence prevents subtle bugs in high-concurrency apps.

Volatile, Memory Barriers, and Synchronized Blocks: Clarifications

Volatile and Data Visibility

Consider this example: 

volatile boolean ready = false;
int data = 0;

Thread 1:
    data = 42;       // (1) Write data
    ready = true;    // (2) Set ready flag

Thread 2:
    if (ready) {
        // Can safely read 'data' here, guaranteed to see 42
    }

Explanation: The volatile keyword on ready ensures that when Thread 2 sees ready == true, it also sees the updated data value written before it in Thread 1. This is because volatile variables create memory barriers that enforce ordering and visibility guarantees.

What Are Memory Barriers?

A memory barrier (or fence) is a CPU instruction that prevents certain types of reordering of read and write operations by the compiler or CPU. They ensure that:

  • Writes before the barrier become visible to other threads before writes after the barrier.
  • Reads after the barrier see the effects of writes that happened before it.

In Java, operations on volatile variables insert these barriers, making changes visible and ordered across threads.

Are Memory Barriers Per Thread?

Yes, memory barriers affect the executing thread's view of memory and ensure that its operations are properly ordered and visible to other threads. Each CPU core (and the thread running on it) respects these barriers to maintain coherence and visibility.

Synchronized Blocks and CPU Core Scheduling

When Thread 1 enters a synchronized block (acquiring a monitor lock) on Core 1, it prevents other threads from entering the same synchronized block at the same time, regardless of which core they run on.

However, Thread 2 can still be scheduled on any core, including Core 1. It just won't be able to enter that synchronized block until Thread 1 releases the lock.

So, synchronized locks are about mutual exclusion on the monitor object, not about restricting thread scheduling on cores.

Summary:

  • volatile guarantees visibility and ordering of variables through memory barriers.
  • Memory barriers prevent CPU/compiler reordering and ensure proper cross-thread visibility.
  • Memory barriers are effective per thread/core to maintain a consistent memory view.
  • synchronized blocks enforce exclusive access to a monitor, but threads can still run on any CPU core; they just wait for the lock to be free.

Monitor Locks: What Are They and How Are They Implemented?

In Java, every object has an associated monitor which is a mutual exclusion lock used to synchronize access to critical sections.

Key Components of a Monitor

  • Lock Owner: The thread currently holding the lock.
  • Entry Queue: Threads waiting to acquire the lock.
  • Wait Queue: Threads waiting inside the monitor (after calling wait()).

Low-Level Implementation Details

The JVM uses object headers to store lock information. These headers include:

  • Mark Word: Contains lock state and owner thread info.
  • Lock States: Unlocked, Biased, Lightweight, Heavyweight locks.

JVM employs a lock escalation strategy:

  • Biased Locking: Optimizes for uncontended locks by biasing towards a thread.
  • Lightweight Locking: Uses atomic instructions to avoid blocking.
  • Heavyweight Locking: Falls back to OS mutex when contention is high.

This layered approach balances performance and correctness in synchronized blocks.

Key Takeaways

1. Memory Model: Rules for visibility & ordering.

2. Cache Coherence: Syncs caches across cores (MESI protocol).

3. Models vary: Sequential (safe) vs. Relaxed (fast).

4. In Java: Use volatile & locks for coherence.

5. Bugs? Stale reads, reordering — fixed by barriers.

6. Monitor locks provide synchronized mutual exclusion, implemented efficiently by JVM.
