3.7 Real-World: Concurrent Bank Transfers

The Ultimate Test of Thread Safety

How to move money safely between accounts under massive concurrency

Chapter 3 – Synchronization & Thread Safety

The Challenge: Money Must Never Disappear

Two threads transfer money between the same accounts at the same time.
Requirements:

  • Total money in system must remain constant
  • No overdrafts allowed
  • 1000+ concurrent transfers
  • Zero lost or duplicated money
This is the gold standard test of correct synchronization.

// DANGEROUS — Race condition!
public void transfer(Account from, Account to, int amount) {
    from.balance -= amount;   // Read-modify-write
    to.balance += amount;     // Race!
}
Result: Total money can become $1900 or $2100 instead of $2000
Lost or duplicated dollars!

Solution 1: Global Lock (Simple but Slow)

private static final Object globalLock = new Object();

public void transfer(Account from, Account to, int amount) {
    synchronized(globalLock) {
        from.balance -= amount;
        to.balance += amount;
    }
}
Pros: Correct, simple
Cons: Only one transfer at a time → terrible throughput

Solution 2: Per-Account Locks + Ordering

public class Account {
    private final Object lock = new Object();
    private long balance;

    public void transfer(Account to, long amount) {
        Account first = this.id < to.id ? this : to;
        Account second = this.id < to.id ? to : this;

        synchronized(first.lock) {
            synchronized(second.lock) {
                if (balance >= amount) {
                    balance -= amount;
                    to.balance += amount;
                }
            }
        }
    }
}
Why ordering? Prevents deadlock (always lock in global order)

Solution 3: ReentrantLock with tryLock() — No Deadlock

private final Lock lock = new ReentrantLock();

public boolean transfer(Account to, long amount) {
    if (!lock.tryLock()) return false;
    if (!to.lock.tryLock()) {
        lock.unlock();
        return false;
    }
    try {
        if (balance >= amount) {
            balance -= amount;
            to.balance += amount;
            return true;
        }
        return false;
    } finally {
        to.lock.unlock();
        lock.unlock();
    }
}
Avoids deadlock by trying both locks
Fallback: retry or queue

Production Pattern: Transfer Service

@Service
public class TransferService {
    private final ExecutorService executor = Executors.newFixedThreadPool(16);

    public CompletableFuture transfer(Account from, Account to, long amount) {
        return CompletableFuture.supplyAsync(() -> {
            // Ordered locking
            Account a = from.id < to.id ? from : to;
            Account b = from.id < to.id ? to : from;

            synchronized(a) {
                synchronized(b) {
                    if (from.balance >= amount) {
                        from.balance -= amount;
                        to.balance += amount;
                        return true;
                    }
                    return false;
                }
            }
        }, executor);
    }
}
Real bank systems use:
• Ordered locking
• Retry on failure
• Distributed transactions (XA, Saga)
• Eventual consistency

Key Takeaways

1. Bank transfers = ultimate thread-safety test

2. Never do balance -= amount without proper locking

3. Global lock = correct but slow

4. Per-account lock + ordering = correct + scalable

5. tryLock() = deadlock-free

6. Production: ordered locking + async + retry
