Chapter 4 – Executors & Thread Pools

Chapter 4 Capstone

You now know how to use executors, pools, and parallelism.
This final section teaches you how to use them correctly in production.

Golden Rule:
Prefer high-level constructs. Never manage threads manually.

The Ultimate Do / Don’t Guide

Do This Best Practice
  • Use ExecutorService from Executors or custom
  • Always shutdown() + awaitTermination()
  • Prefer submit() + Future or CompletableFuture
  • Use bounded queues and rejection policies
  • Size pools based on CPU vs I/O bound
  • Monitor with Micrometer / JMX
  • Use parallelStream() for CPU-bound data processing
  • Never block commonPool()
Never Do This Anti-Pattern
  • new Thread(runnable).start() in loops
  • Executors.newCachedThreadPool() in servers
  • Unbounded queues (LinkedBlockingQueue without limit)
  • Blocking I/O in commonPool() or parallel streams
  • Creating thousands of short-lived threads
  • Forgetting to shutdown executors
  • Using java.util.Timer
  • Manual thread management in Spring

Thread Pool Sizing Cheat Sheet

CPU-bound: N = number of cores
I/O-bound: N = cores × (1 + average wait / compute time)

@Async Pool
@Bean
public TaskExecutor asyncExecutor() {
    ThreadPoolTaskExecutor e = new ThreadPoolTaskExecutor();
    e.setCorePoolSize(8);
    e.setMaxPoolSize(64);
    e.setQueueCapacity(500);
    e.setThreadNamePrefix("async-");
    e.setRejectedExecutionHandler(new CallerRunsPolicy());
    return e;
}

Graceful Shutdown Pattern

@PreDestroy
public void shutdown() {
    executor.shutdown();
    try {
        if (!executor.awaitTermination(60, TimeUnit.SECONDS)) {
            executor.shutdownNow();
            executor.awaitTermination(60, TimeUnit.SECONDS);
        }
    } catch (InterruptedException e) {
        executor.shutdownNow();
        Thread.currentThread().interrupt();
    }
}

Final Chapter 4 Takeaways

You Are Now Production-Ready
  • Never use new Thread() — ever
  • Always use ExecutorService or higher-level APIs
  • Size pools correctly: CPU-bound ≈ cores, I/O-bound ≈ 50–200
  • Use bounded queues + CallerRunsPolicy
  • Always shutdown gracefully
  • Never block commonPool() or parallel streams
  • Monitor active threads, queue size, rejected tasks
  • Prefer CompletableFuture and reactive for new code
