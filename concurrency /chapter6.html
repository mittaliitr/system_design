0.5 OS Threading: Kernel vs. User Threads

Who Really Manages Your Threads?

Chapter 0 – Computer Architecture & Concurrency Foundations

Think of a Busy Restaurant

Waiters (threads) take orders, serve food, and clean tables. But who manages them?

Analogy: Kernel threads are like official staff managed by the restaurant owner (OS kernel). User threads are like self-organized volunteers managed by the head waiter (your program).

Threads at the OS Level

A thread is the smallest unit of execution. The OS decides:

  • When a thread runs (scheduling)
  • Which CPU core it uses
  • How long it runs (time slicing)
Key Question: Who creates and schedules threads — the OS kernel or your program?

Kernel Threads vs. User Threads

Kernel
Kernel-Level Threads
Pros:
- True parallelism (multi-core)
- Blocking calls don't freeze app
- OS schedules efficiently

Cons:
- Expensive to create/switch
- Limited (thousands max)
User
User-Level Threads
Pros:
- Lightweight (100K+ possible)
- Fast context switch
- Portable

Cons:
- One block → all blocked
- No true parallelism 
// Java uses KERNEL threads!
Thread t = new Thread(() -> {
    System.out.println("Hello from kernel thread!");
});
t.start();  // OS schedules on real CPU core

Thread Mapping: 1:1, M:1, M:N

How do user threads map to kernel threads?

1:1 (Java, Windows, Linux)

Each user thread → one kernel thread
Best for performance

M:1 (Old Green Threads)

Many user threads → one kernel thread
Lightweight but no parallelism

M:N (Hybrid – Go, Erlang)

Many user → few kernel threads
Best of both worlds

Java Uses 1:1 Kernel Threads

Since Java 1.2, java.lang.Thread maps 1:1 to kernel threads.

Why? - True parallelism on multi-core
- Blocking I/O doesn't freeze JVM
- OS handles scheduling fairly 
// Each Thread = OS kernel thread
ExecutorService exec = Executors.newFixedThreadPool(4);
exec.submit(() -> heavyTask());  // Runs on real CPU core!

But... Creating 10,000+ threads is expensive → enter Project Loom (virtual threads)!

Future: Virtual Threads (M:N)

Java 21+ introduces virtual threads — lightweight, user-managed threads that run on a small pool of kernel threads.

Revolutionary: Thread.startVirtualThread() → millions of threads, no overhead! 
// Project Loom: M:N model
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> System.out.println("Virtual!"));
}  // Millions possible!

Key Takeaways

1. Kernel threads: Managed by OS → true parallelism.

2. User threads: Managed by app → lightweight but no parallelism.

3. Java uses 1:1 kernel threads (since 1.2).

4. Project Loom: Virtual threads → M:N, millions of threads.

5. Blocking call in kernel thread? Only that thread waits.
