Imagine a Shared Bathroom

Two people (threads) want to use the same bathroom (shared resource). Without a lock, chaos ensues!

Analogy: A lock is the bathroom door bolt. Only one person can enter at a time. The critical section is the time inside the bathroom.

Critical Section: The Danger Zone

A critical section is code that accesses shared mutable state and must not be executed by more than one thread at a time.

Critical Section
Only 1 thread allowed!
Race Condition Example: Two threads increment counter++ → final value may be wrong!

Lock (Mutex): Mutual Exclusion

A mutex (mutual exclusion) is a synchronization primitive that ensures only one thread enters a critical section at a time. 

// Java: Simple lock
synchronized(this) {
    counter++;  // Critical section protected!
}

// Pseudocode: Spinlock using TAS

Key: test_and_set is atomic — CPU guarantees no interleaving. This is the foundation of all locks!

From TAS to Java synchronized

Java’s synchronized uses:

  • MonitorEnter/MonitorExit bytecode
  • JVM → OS mutex (pthread_mutex on Linux)
  • Under the hood: TAS or CAS
// Java → JVM → OS → CPU
public synchronized void increment() {
    counter++;
}
// → Uses atomic TAS/CAS + memory barriers

Spinlock vs Blocking Lock

Spinlock and Blocking Lock are two fundamental approaches to managing access to shared resources.

Spinlock (TAS)

while (TAS(lock)) { }  // Busy-wait
// Critical section
lock = 0

- The thread busy-waits (spins), continuously checking the lock until it becomes available.
- Fast if the lock is held briefly, avoiding overhead of putting thread to sleep and waking it.
- Wastes CPU cycles if the lock is held for longer.

Blocking Lock

acquire() → sleep if locked
// Wake up when free
release() → wake waiter

- The thread goes to sleep if the lock is held, freeing the CPU.
- Efficient for longer wait times.
- Involves context switches and scheduler overhead.

Comparison Table

Aspect Spinlock Blocking Lock
Waiting Style Busy-waiting (CPU spinning) Thread sleeps (blocks)
CPU Usage High when waiting Low
Overhead Low (no context switch) Higher (context switches)
Lock Hold Time Best for very short durations Best for longer durations
Suitable Usage OS kernels, low contention User applications, high contention
Fairness Usually unfair (no guaranteed order) Fairer (based on scheduler)

Modern JVM Locking

The JVM optimizes locking using a multi-stage approach:

  • Biased Locking: Initially biases a lock towards a single thread to avoid synchronization overhead when uncontended.
  • Lightweight Locking: Uses spinlock-like behavior for short waits without going to OS-level blocking.
  • OS Mutex Escalation: For longer contention or waits, escalates to OS mutexes where threads block and get scheduled efficiently.
Summary: JVM tries to keep locking cheap for the common case (no or low contention) and only pays OS overhead when really needed.

Key Takeaways

1. Critical Section: Code accessing shared data → must be protected.

2. Mutex (Lock): Ensures only one thread enters.

3. Test-and-Set (TAS): Atomic CPU instruction → core of all locks.

4. Java synchronized → built on TAS + OS mutex.

5. volatile ≠ lock — only visibility, not atomicity!
