3.6 The volatile Keyword

Visibility Without Atomicity

The most misunderstood keyword in Java concurrency

Chapter 3 – Synchronization & Thread Safety

volatile: One Word, Two Guarantees

volatile is not a lightweight lock.
It gives you exactly two things:

1. Visibility: Writes are immediately visible to other threads
2. Ordering: No reordering of volatile reads/writes
It does NOT give you atomicity for compound operations

The Classic Visibility Bug

Without volatile (Broken)
private boolean running = true;

Thread worker = new Thread(() -> {
    while (running) {
        // spins forever!
    }
});

worker.start();
Thread.sleep(100);
running = false;  // Never seen by worker
With volatile (Fixed)
private volatile boolean running = true;

Thread worker = new Thread(() -> {
    while (running) {
        // sees change → exits
    }
});
volatile forces:
to Write → flush store buffer → L1 cache → visible
to Read → invalidate cache line → fresh value

volatile Inserts 4 Memory Barriers

graph TD A[Normal writes] --> B[volatile write] B --> C[StoreStore Barrier] C --> D[StoreLoad Barrier] E[volatile read] --> F[LoadLoad Barrier] E --> G[LoadStore Barrier] style B fill:#8e44ad,stroke:#8e44ad,color:white style E fill:#8e44ad,stroke:#8e44ad,color:white
JMM Specification:
to volatile write → StoreStore + LoadStore
to volatile read → LoadLoad + LoadStore

Happens-Before Relationships

volatile Establishes Happens-Before
  • Write to volatile → all subsequent reads of that volatile
  • All writes before volatile write → visible after volatile read
  • All writes after volatile read → visible before volatile write
int data = 0;
volatile boolean ready = false;

Thread 1:
    data = 42;
    ready = true;  // Flush data

Thread 2:
    if (ready) {   // Fresh read
        assert data == 42;  // Guaranteed!
    }

volatile ≠ Atomic (The Big Misunderstanding)

volatile long is NOT atomic!
volatile long counter = 0;

thread1: counter++;  // 3 steps → race!
thread2: counter++;  // Lost update possible
counter++ is NOT atomic even if counter is volatile!
Use AtomicLong instead.
Correct: AtomicLong
AtomicLong counter = new AtomicLong(0);

counter.incrementAndGet();  // Truly atomic

When to Use volatile

Perfect for:
to One writer, many readers
to Flags (boolean done)
to Status fields
to "Published" references (with final fields) 
// One writer
private volatile boolean shutdownRequested = false;

public void shutdown() { shutdownRequested = true; }

private void loop() {
    while (!shutdownRequested) { /* work */ }
}

// Publish immutable object
private volatile Config config;

public void updateConfig(Config newConfig) {
    this.config = newConfig;  // Safe if Config is immutable
}

Key Takeaways

1. volatile = visibility + ordering

2. Forces flush from register/store buffer to cache

3. Inserts 4 memory barriers

4. Establishes happens-before

5. NOT atomic for compound operations (++, etc.)

6. Use for flags, status, one-writer patterns

7. volatile long/double is atomic — only 64-bit exception
