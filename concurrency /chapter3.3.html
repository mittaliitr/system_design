3.3 wait(), notify(), notifyAll()

Thread Communication Inside the Monitor

The classic producer-consumer pattern — finally explained correctly

Chapter 3 – Synchronization & Thread Safety

From Locking to Communication

synchronized gives you mutual exclusion.
wait()/notify() gives you cooperation between threads.

Analogy: Locks = bathroom door.
wait()/notify() = knocking and saying “I’m done!”

The Trio: wait(), notify(), notifyAll()

wait()
public final void wait() throws InterruptedException
Releases the monitor and sleeps until notified or interrupted.
  • Must own the monitor
  • Re-acquires lock on wakeup
  • Spurious wakeups possible
notify()
public final void notify()
Wakes one waiting thread (arbitrary choice).
  • Must own the monitor
  • No guarantee which thread wakes
notifyAll()
public final void notifyAll()
Wakes all waiting threads — they compete for lock.
  • Safest choice in most cases
  • Used in producer-consumer

Rules You Must Never Break

1. wait(), notify(), notifyAll() must be called inside synchronized block on the same object
2. Always check condition in a loop (spurious wakeups)
3. Prefer notifyAll() over notify() unless proven safe 
// WRONG — IllegalMonitorStateException!
obj.wait();

// CORRECT
synchronized(obj) {
    while (!condition) {
        obj.wait();  // Note: while, not if!
    }
}

Producer-Consumer with wait()/notifyAll()

Producer
synchronized(buffer) {
    while (buffer.isFull()) {
        buffer.wait();  // Release lock, sleep
    }
    buffer.add(item);
    buffer.notifyAll(); // Wake consumers
}
Consumer
synchronized(buffer) {
    while (buffer.isEmpty()) {
        buffer.wait();  // Release lock, sleep
    }
    Item item = buffer.remove();
    buffer.notifyAll(); // Wake producers
}
sequenceDiagram participant P as Producer participant B as Buffer Monitor participant C as Consumer P->>B: acquire() Note over B: full → wait() P->>B: wait() → release lock C->>B: acquire() C->>B: remove item C->>B: notifyAll() B-->>P: wake up → re-acquire lock P->>B: add item P->>B: notifyAll()

Spurious Wakeups: The Hidden Dragon

Real JVM behavior: A thread can wake from wait() without being notified!
Fix: while (condition) not if (condition) 
// WRONG — vulnerable to spurious wakeup
synchronized(lock) {
    if (!ready) lock.wait();
    consume();
}

// CORRECT
synchronized(lock) {
    while (!ready) lock.wait();
    consume();
}

Modern Java: Prefer java.util.concurrent

Old: wait()/notify() — error-prone
New: BlockingQueue, CountDownLatch, CompletableFuture 
// Modern producer-consumer (no wait/notify!)
BlockingQueue queue = new ArrayBlockingQueue<>(10);

executor.submit(() -> {
    while (true) {
        queue.put(produce());  // Blocks when full
    }
});

executor.submit(() -> {
    while (true) {
        Item item = queue.take();  // Blocks when empty
        consume(item);
    }
});

Key Takeaways

1. wait() releases lock + sleeps

2. notifyAll() is safer than notify()

3. Always call inside synchronized on same object

4. Always use while (condition) — never if

5. Prefer java.util.concurrent in new code

6. Understand it — you’ll see it in legacy systems and interviews
