Chapter 3 – Synchronization & Thread Safety

synchronized Methods vs. Blocks

synchronized methods are convenient — but they lock on the wrong object most of the time.

Rule #1: Never use synchronized methods in real code.
Always use synchronized(lock) blocks with a private lock object.

Method vs. Block: The Difference

Synchronized Method Avoid 
public synchronized void increment() {
    count++;
}

// Static method locks on Class object
public static synchronized void incStatic() {
    staticCount++;
}
Locks on this (instance) or MyClass.class (static)
Synchronized Block Recommended 
private final Object lock = new Object();

public void increment() {
    synchronized(lock) {   // Fine-grained
        count++;
    }
}
You choose the lock object → full control

Reentrancy: The Hidden Superpower

private final Object lock = new Object();

public void outer() {
    synchronized(lock) {
        System.out.println("Outer acquired");
        inner();  // Re-acquires the same lock!
    }
}

public void inner() {
    synchronized(lock) {
        System.out.println("Inner acquired");  // Works!
    }
}
ReentrantLock: Monitor keeps a counter + owner thread
Same thread can re-enter → no self-deadlock
sequenceDiagram participant T as Thread participant M as Monitor T->>M: acquire() → count=1, owner=T T->>M: acquire() → count=2 (reentrant!) T->>M: release() → count=1 T->>M: release() → count=0

Top 5 Pitfalls (and Fixes)

Locking on this / Class
public synchronized void bad() { ... }  // Exposed!
Fix: private final Object lock
Locking on String / Integer
synchronized("LOCK") { ... }  // Interned → global lock!
Fix: new Object()
Changing lock object
private Object lock = new Object();
lock = new Object();  // Breaks synchronization!
Fix: final Object lock
Locking on null
private Object lock;
synchronized(lock) { ... }  // NPE!
Fix: initialize lock

The Gold Standard Pattern

public class SafeCounter {
    private long count = 0;
    private final Object lock = new Object();  // Private + final

    public void increment() {
        synchronized(lock) {
            count++;
        }
    }

    public long get() {
        synchronized(lock) {
            return count;
        }
    }
}
Why this wins:
to Private → no external locking
to Final → never changes
to Fine-grained → only when needed
to Reentrant → safe for nested calls

Key Takeaways

1. Never use synchronized methods in production

2. Always use private final Object lock = new Object()

3. Monitors are reentrant — same thread can re-enter

4. synchronized = acquire → execute → release

5. Provides mutual exclusion + visibility
