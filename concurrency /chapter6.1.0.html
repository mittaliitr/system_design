6.1 Why Virtual Threads?

Platform Threads Are Dead — Long Live Virtual Threads!

The biggest concurrency revolution since Java 5

Chapter 6 – Project Loom

Platform Threads: Expensive & Scarce

For 25 years, every java.lang.Thread was a platform (OS) thread.

Reality: Creating 10,000+ platform threads → OOM, thrashing, death
Result: Everyone uses thread pools → complex, blocking code becomes reactive hell

Platform Threads vs Virtual Threads

Platform Threads Old World
• 1:1 with OS thread
• ~1–8 MB stack
• Expensive context switch
• Max ~10,000–30,000
• Blocking = wasted thread
Virtual Threads (Project Loom) New World
• M:N with carrier threads
• ~Few KB stack
• Cheap context switch
• Millions possible
• Blocking = just pause virtual thread
Metric Platform Thread Virtual Thread
Memory per thread 1–8 MB ~Few KB
Creation cost High Near zero
Max concurrent ~10,000 1,000,000+
Blocking I/O Wastes OS thread Carrier thread freed
Code style Reactive / callbacks Plain blocking code

How Virtual Threads Work

graph TD A[Virtual Thread] -->|blocked on I/O| B[Carrier Thread Pool] A -->|running| C[Mounted on carrier] B -->|unblock| A D[100,000 Virtual Threads] --> B[200 Carrier Threads] style A fill:#7c3aed,stroke:#7c3aed,color:white style B fill:#00b894,stroke:#00b894,color:white
M:N scheduling:
Millions of virtual threads → few carrier (platform) threads
When virtual thread blocks → carrier thread runs another virtual thread

One Million Threads — No Problem

// Java 21+ — This just works!
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 1_000_000).forEach(i -> {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));
            System.out.println("Task " + i + " done");
        });
    });
} // Auto shutdown + join
Result: 1,000,000 tasks → ~few hundred MB RAM → runs in seconds
Same code with platform threads → OOM in < 10,000

The End of Reactive Programming Pain

Before Loom: High concurrency → Reactive (RxJava, Project Reactor)
After Loom: Write simple blocking code → get reactive performance 
// Old reactive hell
userService.findUser(id)
    .flatMap(user -> orderService.findOrders(user))
    .subscribe(orders -> render(orders));

// New: plain Java
User user = userService.findUser(id);     // blocks virtual thread
List orders = orderService.findOrders(user);
render(orders);

Key Takeaways

1. Platform threads = expensive, scarce (max ~10k)

2. Virtual threads = cheap, abundant (millions)

3. M:N scheduling → carrier threads reused

4. Blocking code becomes scalable again

5. No more reactive complexity for concurrency

6. Java 21+ → Executors.newVirtualThreadPerTaskExecutor()
