3.4 ReentrantLock & Condition

The Modern, Flexible Replacement for synchronized + wait/notify

From intrinsic locks to explicit, powerful concurrency

Chapter 3 – Synchronization & Thread Safety

Why ReentrantLock Exists

synchronized is simple but limited:

  • No timeout on lock acquisition
  • No fairness control
  • No multiple conditions per lock
  • No tryLock()
ReentrantLock = synchronized on steroids
Same performance (or better) + massive flexibility

ReentrantLock vs synchronized

synchronized Built-in 
synchronized(lock) {
    while (!ready) lock.wait();
}
lock.notifyAll();
ReentrantLock + Condition java.util.concurrent 
Lock lock = new ReentrantLock();
Condition ready = lock.newCondition();

lock.lock();
try {
    while (!ready) ready.await();
} finally {
    lock.unlock();
}
ready.signalAll();
Feature synchronized ReentrantLock
Timeout No tryLock(5, SECONDS)
Fairness No (unfair) new ReentrantLock(true)
Multiple Conditions One per object lock.newCondition()
Interruptible No lockInterruptibly()
Performance Excellent (biased locking) Same or better

ReentrantLock is Reentrant

Lock lock = new ReentrantLock();

public void outer() {
    lock.lock();
    System.out.println("Outer");
    inner();  // Re-acquires same lock!
    lock.unlock();
}

public void inner() {
    lock.lock();
    System.out.println("Inner");
    lock.unlock();
}
Hold count: Same thread can lock multiple times
Must unlock same number of times

Condition: Multiple Wait Sets Per Lock

Producer
lock.lock();
try {
    while (buffer.full())
        notFull.await();
    buffer.add(item);
    notEmpty.signalAll();
} finally {
    lock.unlock();
}
Consumer
lock.lock();
try {
    while (buffer.empty())
        notEmpty.await();
    item = buffer.remove();
    notFull.signalAll();
} finally {
    lock.unlock();
}
One lock, multiple conditions → precise signaling
No spurious wakeups issue with proper loop

Advanced Features

// 1. Try with timeout
if (lock.tryLock(5, TimeUnit.SECONDS)) {
    try { ... } finally { lock.unlock(); }
}

// 2. Fair lock (FIFO)
Lock fairLock = new ReentrantLock(true);

// 3. Interruptible
lock.lockInterruptibly();  // Responds to interrupt()

// 4. ReadWriteLock for read-heavy
ReadWriteLock rw = new ReentrantReadWriteLock();
rw.readLock().lock();
rw.writeLock().lock();

When to Use Which?

Scenario Use synchronized Use ReentrantLock
Simple mutual exclusion Yes Overkill
Need timeout / fairness No Yes
Multiple conditions No Yes
Performance critical Often faster Comparable

Key Takeaways

1. ReentrantLock = explicit, powerful, modern lock

2. Condition = multiple wait sets per lock

3. Features: timeout, fairness, interruptible, tryLock

4. Always lock() in try, unlock() in finally

5. Use for advanced scenarios — synchronized for simple

6. ReadWriteLock for read-heavy data
