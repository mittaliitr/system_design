1.3 Threads vs. Processes

Lightweight vs. Heavyweight Execution

Why a single Spring Boot instance can handle thousands of users

Chapter 1 – Introduction to Multithreading in Java

Think of a Restaurant

A process is like opening a new restaurant — expensive, isolated, full setup.
A thread is like hiring a new waiter in the same restaurant — fast, shared resources.

Key Insight: One process to many threads to thousands of concurrent users

Real-World: Spring Boot Web Service

A single Spring Boot instance (one JVM process) handles thousands of HTTP requests using multiple threads.

Single Process
@SpringBootApplication
public class App {
    public static void main(String[] args) {
        SpringApplication.run(App.class, args);
    }
}

@RestController

1000+ Concurrent Users
User GET /profile to Thread #1
User GET /profile to Thread #2
User GET /profile to Thread #3
User ... to Thread #N

All in one JVM process
Using Tomcat thread pool 

# application.yml
server:
  tomcat:
    max-threads: 200   # Default thread pool
    min-spare-threads: 10
Result: One process to 200+ concurrent requests to high throughput, low overhead

When to Use Processes vs. Threads?

Use Case Processes Threads Web Server (Spring Boot) Too heavy Perfect Crash Isolation Yes No Microservices One per service Many per service Python GIL Workaround Use processes Blocked

Key Takeaways

1. Processes = isolated, expensive, safe

2. Threads = shared, cheap, fast, risky

3. Spring Boot: 1 process to 200+ threads to thousands of users

4. Threads share heap to need synchronization

5. Use processes for isolation, threads for concurrency
