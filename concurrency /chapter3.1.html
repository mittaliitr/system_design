3.1 The synchronized Keyword

Your First Line of Defense Against Race Conditions

The most important 11 letters in concurrent Java

Chapter 3 – Synchronization & Thread Safety

Welcome to the War on Race Conditions

You now know how to create threads. Now the real challenge begins: making them play nicely together.

The Problem: Multiple threads reading/writing shared mutable state → unpredictable results.
The Solution: synchronized — Java’s built-in mutual exclusion.

The Classic Example: Broken Counter

Without synchronized (Broken)

class Counter {
    int count = 0;

    void increment() {
        count++;  // Not atomic!
    }
}

// 100 threads × 1000 increments → should be 100,000
// Actual result? 73,421 (lost updates!)

With synchronized (Fixed)

class Counter {
    int count = 0;

    synchronized void increment() {
        count++;  // Now atomic!
    }
}

// Result: exactly 100,000
One word — synchronized — saves you from chaos.

How synchronized Actually Works

Every Java object has one monitor (intrinsic lock)
synchronized = acquire monitor → execute → release monitor

Two Ways to Use synchronized

1. Synchronized Method

class Counter {
    private int count = 0;

    // Locks on 'this'
    public synchronized void increment() {
        count++;
    }

    // Static locks on Class object
    public static synchronized void incStatic() {
        staticCount++;
    }
}

2. Synchronized Block (Preferred)

class Counter {
    private final Object lock = new Object();
    private int count = 0;

    public void increment() {
        synchronized(lock) {  // Fine-grained
            count++;
        }
    }
}
Prefer synchronized blocks — more control, better performance, avoids accidental locking on this

What synchronized Actually Guarantees

Guarantee Description
Mutual Exclusion Only one thread in the monitor at a time
Visibility Writes before unlock visible after lock
Happens-Before Unlock → Lock ordering guaranteed
Atomicity For the block/method — no interleaving
synchronized = lock + memory barrier
It’s volatile on steroids.

Top 5 synchronized Pitfalls

1. Locking on wrong object

Integer count = 0;  // Boxing creates new object!
synchronized(count) { ... }  // Race condition!

2. Locking on this in public API

public synchronized void bad() { ... }
// Client can lock on your instance → deadlock risk
Best Practice: Always lock on private final Object lock = new Object();

Key Takeaways

1. synchronized = mutual exclusion + visibility

2. Every object has one monitor (intrinsic lock)

3. Prefer synchronized(block) over method

4. Never lock on this, String, Integer

5. Use private final Object lock for safety

6. synchronized is your first weapon — master it before locks
