JVM Architecture — The Big Picture

A concise, visual explainer of JVM components: class loading, runtime data areas, execution engine (interpreter + JIT), garbage collection, and tooling.

Overview

The JVM is an abstract machine specification + concrete implementations (HotSpot, OpenJ9, GraalVM). It executes Java bytecode and provides runtime services: class loading, memory management (GC), runtime optimization (JIT), threading, and native interfacing.

High-level diagram

Core components

  • Class loader subsystem: loads class files into the runtime, resolves symbolic references, and enforces visibility. Typical hierarchy: Bootstrap → Platform (Extension) → Application.
  • Runtime Data Areas: Method Area (class metadata, runtime constant pool), Heap (all objects, GC-managed), Java Stacks (each thread's frames), PC Registers (per-thread), Native Method Area (for JNI/native code).
  • Execution Engine: Interpreter converts bytecode to machine actions; JIT compiles hot methods to native code (tiered compilation). Runtime services include garbage collection, thread scheduling, and safepoints.
  • Native Interface (JNI): enables interaction between Java and native libraries (C/C++), important for OS integration and performance-sensitive code.

Memory model (brief)

The JVM Memory Model defines visibility and ordering guarantees for threads — it specifies happens-before relationships used by `volatile`, `synchronized`, and concurrent utilities. For implementation, HotSpot separates generations (Young/Old), metaspace for class metadata, and uses per-region or per-generation GC algorithms.

Garbage collection (GC)

Multiple GC algorithms target throughput, latency, or footprint: Serial, Parallel (Throughput), CMS (deprecated), G1 (default in many versions), ZGC, Shenandoah, and region-based collectors. Modern collectors aim for low pause times and predictable latency for cloud-native apps.

JIT & Runtime optimization

HotSpot uses a tiered compilation strategy: interpreter & C1 (client) for quick compilation, C2 (server) for heavy optimization. Profiling, inlining, escape analysis, and speculative optimizations improve performance over time. Graal provides an alternative JIT/AOT for polyglot runtimes and native images.

Threading & Concurrency

The JVM provides the Java Memory Model primitives (volatile, synchronized, locks, java.util.concurrent). The runtime schedules OS threads (1:1 model) and provides monitors, biased locking, and lock elision optimizations.

Tooling & observability

Essential tools: jmapjstackjstatjcmdjinfo. Flight Recorder (JFR), Java Mission Control (JMC), VisualVM for profiling and diagnostics.

Putting it together — lifecycle of a class

  1. Load: Class loader locates `.class` bytes and creates a Class object in the method area.
  2. Link: Verification, preparation (allocate static fields), and resolution of symbolic refs.
  3. Initialize: Run static initializers and assign explicit initial values.
  4. Execute: Methods executed by the interpreter or compiled by the JIT; objects allocated on the heap and collected by GC when unreachable.

Common GC choices

  • G1: balanced default, region-based, predictable pauses.
  • ZGC / Shenandoah: low-pause collectors for large heaps.
  • Parallel GC: maximize throughput in batch jobs.
