Class Loading & The Module System (JPMS)

How classes get discovered, linked, and initialized in the JVM — and how JPMS (Java 9+) changes packaging, encapsulation, and runtime composition.

Class Loading Fundamentals

Class loading is the process of locating binary class data (usually from .class files or jars), defining Class objects, linking (verification, preparation, resolution), and initializing static state before use.

The delegation model

A typical JVM uses a parent-first delegation model: each ClassLoader delegates to its parent to load a class before attempting to load it itself. Common loaders:

  • Bootstrap ClassLoader — loads core JDK classes (rt.jar / modules).
  • Platform (Extension) ClassLoader — loads platform classes and extensions.
  • Application (System) ClassLoader — loads application classes from the classpath.

Custom ClassLoaders

Custom loaders (URLClassLoader or custom implementations) allow isolation, dynamic reloading, plugin systems, and per-appclassloader sandboxing. Important concerns: visibility edges, resource lookup, and avoiding memory leaks (unreleased references preventing GC of classes).

Lifecycle: Load → Link → Initialize

  1. Load: Obtain binary and create a Class object.
  2. Link: Verify bytecode, prepare static fields, and resolve symbolic refs.
  3. Initialize: Run static initializers & assign explicit values.

Problems in the Wild

  • NoClassDefFoundError — class missing at runtime (different from ClassNotFoundException thrown by loaders).
  • ClassCastException across classloaders — same class name loaded by different loaders is not the same runtime type.
  • Memory leaks: long-lived classloader references (threads, static caches, JNI) prevent unloading.

Java Platform Module System (JPMS)

Introduced in Java 9, JPMS introduces modules as units of encapsulation and reliable configuration. A module explicitly declares which packages it exports and which modules it requires.

module-info.java basics

module com.example.app {
  requires java.sql;
  requires com.fasterxml.jackson.databind;
  exports com.example.api;
  opens com.example.internal to com.example.tools; // reflective access
}

Key concepts

  • Strong encapsulation: packages not exported are inaccessible at compile-time and runtime (reflection blocked unless opened).
  • Module path vs Classpath: modules live on module-path; classpath is still supported but treated as an automatic unnamed module.
  • Automatic modules: jars on module-path without module-info become automatic modules (exports all packages, reads all unnamed modules).
  • Services: `uses` / `provides ... with` for service loader declarations and implementations.

Class Loading under JPMS

Modules change visibility and resolution: the module system performs graph-based readability checks at link time. The runtime maps modules to classloader spaces; unnamed modules (classpath) are readable by default, but modular jars are isolated unless explicit readability edges exist.

Note: JPMS is not a classloader replacement — it complements classloaders with a higher-level graph of module readability and encapsulation which the runtime enforces.

Migration tips (to modules)

  • Start by modularizing leaf modules with clear APIs (`exports`) and no reflective access.
  • Use `--patch-module` for gradual migration and `--add-exports`/`--add-opens` only as stopgaps.
  • Prefer `jlink` to create small runtime images containing only required modules (great for containers).
  • Third-party libraries without module-info can be placed on the classpath or module-path as automatic modules — beware split packages.

Tools & debugging

  • jdeps — analyze dependencies and detect JDK internal API usage.
  • jcmd VM.class_hierarchy — inspect class and module relationships (vendor-specific).
  • --describe-module and --list-modules JVM flags to inspect resolved modules at runtime.

Common commands

# Analyze dependencies
jdeps --multi-release 11 --recursive myapp.jar

# Run with module-path
