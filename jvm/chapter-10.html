Project Loom: Virtual Threads Are Not Threads

A clear explanation of virtual threads, continuations, structured concurrency, and the practical changes they bring to writing concurrent Java code.

1 — The core idea

Project Loom introduces virtual threads — lightweight, user-mode threads that map many logical threads onto a smaller number of platform (OS) threads. They make blocking I/O cheap again by eliminating the need for complex asynchronous APIs for many workloads.

2 — Virtual threads vs platform threads

Platform threadVirtual thread
RepresentationMapped 1:1 to OS threadsUser-mode, scheduled by the JVM onto carrier threads
CostHigh (stack, OS resources, expensive creation)Low (smaller default stack, cheap creation)
BlockingBlocks OS threadBlocks virtual thread; carrier thread is freed to run others
Use casesLong-running, pinned tasks interacting with native codeHigh-concurrency server tasks, per-request handlers, background tasks

3 — How blocking becomes cheap

When a virtual thread performs a blocking call (e.g., socket read, Thread.sleep), the JVM parks the virtual thread and un-maps it from the carrier (OS) thread, which can continue running other virtual threads. This requires the JVM to manage continuations-style snapshots of execution state efficiently.

4 — Continuations & scheduling

Continuations capture the point of execution so the runtime can suspend and resume fiber-like units. Loom uses continuations under the hood to implement virtual threads; developers rarely interact with continuations directly but benefit from their semantics.

5 — Structured Concurrency

Structured concurrency provides a discipline for composing concurrent tasks so lifetimes are bound to lexical scopes. Loom promotes APIs like StructuredTaskScope that make concurrent code easier to reason about and to handle exceptions and cancellations deterministically.

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
  var f1 = scope.fork(() -> fetchUser());
  var f2 = scope.fork(() -> fetchOrders());
  scope.join();           // wait for tasks
  scope.throwIfFailed();  // propagate first failure
  return new Result(f1.resultNow(), f2.resultNow());
}

6 — Practical examples

Replacing thread-per-request in servers:

// old: create platform thread
new Thread(() -> handleRequest(req)).start();

// new: virtual thread (Loom)
Thread.startVirtualThread(() -> handleRequest(req));

Start hundreds of thousands of virtual threads for high concurrency without massive resource cost.

7 — Interop & pitfalls

  • Blocking native code: If native code blocks a carrier thread, it can stall virtual threads; use ScopedValue or offload to dedicated platform threads when necessary.
  • Thread-locals: ThreadLocal behaves differently — virtual threads inherit values at creation; prefer ScopedValue for context propagation.
  • Pinning: Some operations require pinning a virtual thread to a carrier (e.g., JNI calls that touch thread-local native state).
  • Resource management: Structured concurrency helps avoid leaking tasks; still close sockets and streams.

8 — Performance characteristics

Virtual threads reduce contention and context-switch overhead visible with many blocked platform threads. However, for CPU-bound, long-running tasks, platform threads (or dedicated executor pools) can still be a better fit. Measure with realistic loads.

10 — Migration guidance

  • Start by using virtual threads for IO-bound request handlers.
  • Audit JNI/native libraries and any code that blocks carrier threads.
  • Replace ThreadLocal usage with ScopedValue where appropriate.
  • Use StructuredTaskScope to control lifecycles and handle exceptions.
  • Benchmark with realistic concurrency patterns.

Quick reference

Key APIs: Thread.startVirtualThread, StructuredTaskScope, ScopedValue, Continuation (internal/preview).

When to prefer virtual threads

  • Handling many concurrent short-lived requests
  • Replacing callback-heavy async code with straightforward blocking code
  • Simplifying concurrency for IO-heavy servers

When to be careful

  • Code that relies on thread identity or native thread-local state
  • Long-running CPU-bound work — consider using a dedicated thread pool
  • Blocking inside synchronized sections that assume limited threads
