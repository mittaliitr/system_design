JIT Compilation — From Interpreter to Machine Code

How the JVM transforms portable bytecode into fast native code: tiers, profiling, optimizations, and the lifecycle of compiled code.

Why JIT exists

The JVM starts by interpreting bytecode for fast startup and low memory overhead. Over time it profiles running code to find hot spots and compiles those to optimized native code — combining portability with high performance.

High-level flow

Tiered compilation

Most HotSpot JVMs use multiple tiers: interpreter → C1 (client) → C2 (server). Tiered compilation combines quick, low-optimizing compilation for startup with slower, high-optimizing compilation for long-running hot methods.

  • Interpreter: Executes bytecode directly; cheap to start.
  • C1 (Client): Fast compilation, modest optimizations (good for startup).
  • C2 (Server): Slower compile, aggressive optimizations (inlining, escape analysis, loop unrolling).
  • Graal: Alternative JIT/AOT with advanced optimizations and polyglot support.

Profiling & Hotspot detection

The JVM profiles execution to discover hot methods/loops using counters and sampling. When a method's invocation count crosses thresholds, it becomes a candidate for compilation.

Important flags: -XX:CompileThreshold, -XX:+TieredCompilation, -XX:FreqInlineSize.

Key optimizations performed by JIT

OptimizationWhat it does
InliningReplace a call with the callee's body to expose further optimizations.
Escape analysisDetect objects that don't escape a method/thread and allocate them on the stack or eliminate them.
Scalar replacementBreak an object into primitive fields when it's stack-allocated.
Loop unrolling & vectorizationTransform loops for better throughput and CPU utilization.
Speculative optimizationAssume certain conditions (class shapes, monomorphic call sites) and optimize; will deopt if assumption fails.

Deoptimization & Safepoints

When speculative assumptions become invalid (e.g., a new class is loaded that changes a virtual dispatch), the JVM can deoptimize — revert optimized code back to interpreted frames. Safepoints are global pauses where the JVM can perform GC, deopt, and class unloading safely.

Code Cache & Limits

Compiled native code is stored in the code cache. Monitor via -XX:+PrintCompilation and -XX:+PrintCodeCache. If the code cache fills, compilation can stall — flags like -XX:ReservedCodeCacheSize matter.

AOT (Ahead-Of-Time) & Graal Native Image

GraalVM supports AOT compilation into native images (fast startup, small footprint) at the cost of many dynamic features. HotSpot also supports limited AOT. Choose AOT for short-lived cloud functions or strict startup constraints.

Observability & Tools

  • Verbose compilation: -XX:+PrintCompilation, -XX:+LogCompilation
  • Assembly: -XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly (requires hsdis)
  • Profilers: Java Flight Recorder (JFR), Java Mission Control, async-profiler
  • Graal tooling: VisualVM plugins, Graal compiler logs

Performance tips

  • Keep hot paths small and stable to allow inlining.
  • Avoid excessive class loading during steady-state to reduce deopts.
  • Use escape-analysis-friendly code (favor immutable small objects).
  • Measure with JFR + async-profiler before tuning.
  • Consider Graal native-image for startup-sensitive workloads, but test reflection/service-loader use.

Quick flags cheat-sheet

# Tiered compilation (default)
-XX:+TieredCompilation

# Compilation verbosity
-XX:+PrintCompilation
-XX:+LogCompilation -XX:LogFile=compile.log

# Code cache
-XX:ReservedCodeCacheSize=240m

# Profiling
-XX:CompileThreshold=10000

Common commands

# Record runtime (JFR)
java -XX:StartFlightRecording=duration=60s,name=run1 -jar app.jar

# View compiled methods
jcmd <pid> Compiler.print_native_code_cache
